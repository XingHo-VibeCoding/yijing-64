## 1. 背景与问题

### 1.1 问题陈述

> 「《周易》真正困难的地方并不是内容本身，而是它特殊的表达方式——高度凝练的古文、抽象的卦象符号，以及复杂的卦序、爻变与空间关系，往往让许多人还没真正开始理解，就已经望而却步。」
> —— 引自周易学习网的自我分析，比我们自己的拆解更准确，直接采用

翻译成用户能感知的三句话：

| # | 用户的实际卡点 | 具体表现 |
| --- | --- | --- |
| 1 | **卦象认不出** | 看到 ䷔，说不出这是第几卦、叫什么 |
| 2 | **卦序记不住** | 知道乾、坤，但第 17 卦是什么？ |
| 3 | **古文读不进** | 不看白话读不懂；看了白话又变成「只看白话不看原文」 |

### 1.2 市场空缺（来自 research.md 第 5 节）

**「记忆」和「读原文」在这个品类里是分开的，没人合起来。**

- 易经闯关（最直接的竞品）：有完整记忆闭环（18 个页面 / 6 个闯关章节 / 星级成就 / 薄弱项），**但全站只有 64 个卦象，没有卦辞、没有爻辞、没有白话**
- daooracle.life：文本最全、来源标注最好，**但零记忆功能**
- 爱周易 / 易经宝典：两者都有，但**被 iOS 17+ 锁死**，Android 与桌面用户全被排除

→ **「网页端 + 记忆闭环 + 原文分层」这个交集是空的，这就是本产品的位置。**

### 1.3 三条不可动摇的产品边界（v1.2 修正）

1. **起卦保留，但卦只能「释义」，不能「断事」。**
   起卦是用户走进易经最自然的入口，**它必须留下，而且要放在首页最显眼的位置**。但解读严格限定在「这一卦在讲什么」——**不允许**输出对未来的断言、对具体事项的判断、或「宜 / 不宜」式的建议。卦不是判决书，是一段可以被读懂的话。

2. **吉凶不回避，但方向固定：吉卦戒骄，凶卦劝慰。**
   《周易》原文里本来就大量出现「吉」「凶」「无咎」，回避它等于阉割文本。本产品的做法是给吉凶一个**固定的、非预测性的解读方向**：吉卦提醒「莫骄躁，顺境最容易松懈」，凶卦劝慰「运随时变，困局不是终局」。**这是价值观引导，不是运势判定。**

3. **原文和解读必须分层可见。** 用户要能一眼分清「这是《周易》里的话」还是「这是本项目的理解」。

## 2. 目标用户与场景

### 2.1 用户

**对易经感兴趣、但不是为了算命迷信的人。**

具体一点：他们**会用起卦**——起卦对他们意味着好奇、仪式感，以及一种与古人对话的方式；但他们**不接受**「卦这么说了，所以就这么办」，也不接受有人拿卦象来吓唬自己或安慰自己。

### 2.2 四个核心场景（本期全部服务，优先级 D > A > B > C）

| 场景 | 用户行为 | 本期是否服务 |
| --- | --- | --- |
| **D · 起了那一卦** | 好奇掷了一卦，看到卦象后想知道：**这一卦到底在讲什么？** | ✅ **核心（入口）** |
| **A · 通勤 15 分钟** | 刷到一卦，想立刻知道：这是第几卦、叫什么、大概讲什么 | ✅ 核心 |
| **B · 睡前自测** | 看到卦象能不能说出卦名？第 17 卦是什么？ | ✅ 核心 |
| **C · 周末坐下来读** | 认真读一卦的卦辞、六爻、象辞，并分清原文与解读 | ✅ 核心 |

> **优先级 D > A > B > C。** 顺序是：先让用户「愿意进来」（起卦）→ 再「认得出」→ 然后「记得住」→ 最后「读得深」。
> **场景 D 是 v1.2 新增，它是用户主动打开这个产品的第一动机**；A / B / C 都发生在「已经进来之后」。

## 3. 产品目标 / 非目标

### 3.1 本期目标（25 天）

做一个**网页应用**（前端页面 + 云端数据服务），让用户能：

1. **起一卦，并读到一段严格基于卦象与卦辞、爻辞的解读**（**入口功能，v1.2 新增**）
2. 在 3 次点击内看到任意一卦的卦象、卦辞
3. 做一轮「看卦象选卦名」的测验并看到分数变化
4. 一眼分清哪段是《周易》原文、哪段是本项目的解读
5. **学习进度保存在云端**，不随浏览器缓存清空而丢失

> 形态说明：仍然是「打开网址就能用」的网页——**没有注册、没有登录、没有下载**。云端只承担两件事：下发卦数据、保存学习进度（详见 §7.3）。

### 3.2 本期非目标

- **不做命运判定**：不对未来下断言，不说「你会……」「接下来会……」
- **不做决策建议**：不出现「宜 X」「不宜 Y」「建议你……」，不判断任何具体事项（换工作 / 出行 / 投资 / 感情）的吉凶
- **不做收费解卦**、不做一对一咨询、不做运势推送、不做「今日运势」
- **不做变卦（之卦）推演**：起卦只给**本卦 + 变爻**，明确说明本工具不推演变出的那一卦
- **不做注册与登录**（无手机号、无邮箱、无第三方登录）；本期用匿名标识保存进度
- **不做跨设备同步**（匿名标识绑定当前浏览器，换设备等于重新开始）
- 不做移动 App；服务端**只做两件事**——下发卦数据、保存学习进度，不做其他业务逻辑
- **不采集任何身份信息**（姓名、手机号、邮箱、IP、设备指纹、地理位置一律不落库），不做行为埋点
- 不做十翼（系辞、说卦、序卦、杂卦）
- 不做面向研究者需要的注疏对照与版本考据

## 4. 本期砍掉的功能（以及为什么砍）

> 这是本文档最重要的一节。**做减法不是妥协，而是这个产品的立身之本。**

### 4.1 第一大取舍：保留起卦，砍掉「迷信解读」（v1.2 重写）

> **v1.0 / v1.1 曾把起卦本身列为「第一大砍」，那是错的。** 起卦不是这个产品的风险，而是它最大的入口价值。真正要砍的是**起卦之后那套迷信化的解读方式**。

#### 4.1.1 保留什么：起卦

| | |
| --- | --- |
| **保留的功能** | 起卦（**以铜钱法为主**）、起卦结果页、由卦象与卦辞爻辞生成的解读 |
| **为什么它必须留下** | 一个纯知识工具**没有让人主动打开的理由**。「背 64 卦」是任务，「起一卦看看」是好奇——**好奇才是入口**。起卦之后，「这一卦在讲什么」变成了用户自己的问题，学习动机从外部要求转为内部驱动。**这是整个产品最重要的一次动机设计。** |
| **它同时是差异化** | 头部产品里，爱周易与易经宝典都是 App（被 iOS 17+ 锁死），daooracle.life 文本最全但不做引导，易经闯关有完整记忆闭环却**连卦辞都没有**。**「网页端 + 起卦入口 + 回到原文」这个组合目前是空的。** |
| **解禁条件** | 无需解禁，**这是 P0 功能** |

#### 4.1.2 砍掉什么：三类「迷信解读」

| 砍掉的东西 | 具体表现 | 为什么砍 |
| --- | --- | --- |
| **命运判定** | 「你会遇到贵人」「今年有财运」「此事能成」 | 这是断事，不是释义。**一旦开始对未来下断言，产品就从学习工具变成了算命工具**——目标用户会立刻离开，这是我们唯一真正的自毁路径 |
| **决策建议** | 「宜出行」「不宜投资」「建议你再等等」 | 把卦包装成行动指南，等于替用户做决定。**用户要的是理解一个卦，不是被一个卦指挥** |
| **AI 自由发挥的解卦** | 用大模型生成一段看起来很懂的卦义 | 不是定位冲突，而是**没有可核对的标准**。用户无法判断对错，这与「原文与解读必须分层可见」的信任基础直接矛盾。**解读必须能追溯到具体的卦象、卦辞或爻辞** |

#### 4.1.3 吉凶怎么处理：不回避，给固定方向

**不回避。** 卦辞爻辞原文里本来就大量含「吉」「凶」「无咎」——谦卦爻辞就是「谦谦君子，用涉大川，吉」。回避它等于阉割文本。

**但方向是固定的，由卦的属性决定：**

| 卦的属性 | 解读落点 | 语气示例 |
| --- | --- | --- |
| **吉** | **戒骄躁** —— 顺境最容易松懈，好运不是理所当然 | 「此刻是顺的。但《易》讲得最多的恰恰是：顺的时候最容易走岔。」 |
| **凶** | **劝慰** —— 运随时变，困局不是终局 | 「眼下是难的。但六十四卦排下来，没有一卦能一直难下去——**「无平不陂，无往不复」**。」 |
| 平 / 无咎 | 中性陈述，落在「继续观察」 | 「谈不上吉也谈不上凶，它只是把这件事实话实说。」 |

> **为什么这不是预测**：预测说的是「你会怎样」，这里说的是「你可以怎么看待当下」。**前者替用户判断世界，后者帮用户安顿自己。** 而且这个方向与《周易》本身的内核一致——六十四卦从「乾」开始、以「未济」结束，**《易》从不认为有任何一卦是终点**。

#### 4.1.4 那「会不会被当成算命网站」？

会，这是真实风险，所以要用**结构**而不是口号来区分（见 §9 风险 10）：

1. 解读分三层且顺序固定：**卦象说什么 → 卦辞爻辞怎么讲 → 想跟你说的话**；第三层永远带「非原文」标注（F5 组件）
2. 首页与起卦结果页各有一次明确的边界声明
3. 起卦环节**不提供任何「替用户做决定」的输入**——没有「我该不该辞职」这样的提问框，只掷卦

### 4.2 其余砍掉的功能

| 砍掉的功能 | 为什么砍 |
| --- | --- |
| **十翼全文**（系辞/说卦/序卦/杂卦） | 范围太大。本期只做六十四卦本体：用户连 64 卦都还没认全时，十翼是额外负担 |
| **变卦（之卦）推演、互卦 / 错卦 / 综卦 / 交卦** | 属进阶内容。**起卦得到的变爻只在本卦内解释，不推演变出的那一卦**（v1.2 明确）——之卦是另一套规则体系，本期不碰。daooracle.life 做得很好，但不在这个阶段 |
| **账号体系 / 登录**（v1.1 降级为匿名标识） | 本期**仍然不做**注册与登录——理由不变：登录页是学习工具最大的流失点。但**进度改存云端**（见 F6 与 §7.3），用后台生成的匿名标识关联，全程不出现「注册」字样。**数据结构按可迁移设计**，为 v2.0 的账号体系预留 |
| **跨设备同步 / 社区 / 打卡排行** | 跨设备同步依赖账号，留到 v2.0；社区与排行需要运维成本，远超本期收益 |
| **中英文对照 / 朗读 / 音效 / 卦象分享卡** | 体验增强项，不是核心闭环。爱周易的诵读工作台做得很好，但那是第二层需求 |
| **简体繁体切换** | 有真实需求，但不是早期瓶颈 |
| **先天/后天八卦图、八宫图、卦名次序歌等图表页** | 易经宝典在这一块已经做得很好，重复造轮子不如把力气放在记忆闭环上 |
| **App 上架（iOS / Android）** | 先做网页验证需求；审核与维护成本不属于 25 天内该干的事 |
| **繁简拼音搜索、按上下卦筛选** | 本期只做最简搜索（卦名 + 序号）。中文模糊匹配的范围一旦放开就会失控 |
| **PWA 离线支持** | 需求真实（通勤场景），但优先级低于核心闭环 |

### 4.3 一句话总结

> **起卦留着——它是入口；砍掉的是「拿卦替人做决定」的那部分。**
> 换来的空位是：一个能用起卦把你吸引进来、再用卦辞与爻辞把你留在原文里的网页工具。它做三件事——**认得出卦象、读得懂原文、记得住卦序**。

## 6. 功能详述

### F1 · 首页 / 卦列表页（P0）

**目的**：让用户在 3 秒内看懂这是什么网站，并找到想看的那一卦。

**页面元素**

| 元素 | 说明 |
| --- | --- |
| 站点标题与副标题 | 标题：易经六十四卦学习；副标题一句话说明「不是算命工具」 |
| 定位声明 | 一行文字，明确本页不提供占卜与预测 |
| 卦列表 | 64 项，每项显示：**序号 + 卦符 + 卦名 + 上下卦**（如「15 · ䷎ 谦 · 上坤下艮」） |
| 列表分组 | 按「上经（1–30）/ 下经（31–64）」分两组，带小标题 |
| 测验入口 | 一个显眼按钮：「开始识卦测试」 |

**交互**

- 点击任意一项 → 进入 F2 详情页
- 点击测验入口 → 进入 F3
- 卦列表支持键盘上下移动 + 回车进入（可访问性）

**边界条件**

- 64 卦必须全部可点，**不允许任何一项无内容**
- 列表项在窄屏（手机）下换行显示，不出现横向滚动

**不做**

- 不做首页轮播、不做「每日一卦」推送（属第二阶段）
- 不做搜索框（属 F4）

---

### F2 · 单卦详情页（P0）

**目的**：一页看完一卦，并且**清楚知道每一段话的来源**。

**页面元素（自上而下）**

| 顺序 | 元素 | 内容 |
| --- | --- | --- |
| 1 | 卦头 | 序号 + 卦符（大图）+ 卦名 + 拼音 + 上下卦（上卦/下卦各带自然意象，如「坤 · 地」） |
| 2 | **卦象图** | 六条爻线，**从下往上**绘制，阳爻为实线、阴爻为断线；每爻标注爻题（初九/六二…） |
| 3 | 卦辞 | 原文 + 白话，**各带来源标注** |
| 4 | 象辞 | 原文 + 白话，**各带来源标注** |
| 5 | 爻辞 | 6 条，每条：爻题 + 原文 + 白话 + 小象 |
| 6 | 翻页 | 上一卦 / 下一卦 |
| 7 | 返回 | 回到卦列表 |

**核心交互：原文 / 白话分层切换**

- 页头提供两个开关：「显示原文」「显示白话」
- **默认两个都开**
- 两个都关时，页面提示「你已隐藏全部内容，请打开至少一个」
- 每个文本块**永远带来源标注**，即使用户关了白话，原文上方仍标明「《周易》原文 · 出自 ctext.org 王弼本」

**边界条件**

- 卦象图的爻线**必须按从下往上的顺序**渲染（这是最容易做反的地方）
- 白话为空时，显示「本卦白话待补」，**不允许用原文冒充白话**
- 直接访问某一卦的链接，必须能独立打开（可分享）

**不做**

- 不做注疏对照、不做版本差异、不做英译
- 不做笔记功能（属后续版本）

---

### F3 · 记忆测验页（P0）

**目的**：把「认得出卦象」这件事变成一个可重复、有反馈、看得见进步的动作。

**页面元素**

| 元素 | 说明 |
| --- | --- |
| 题面 | 一张卦象图（大图，六条爻线） |
| 选项 | 3 个卦名按钮（1 正确 + 2 干扰项） |
| 进度 | 「第 N / 20 题」 |
| 计分 | 当前连对数、本轮正确数 |
| 反馈区 | 答后立即显示对错 + 正确答案 + **该卦的卦符与序号** |
| 结果页 | 本轮成绩、错题清单（可点击跳到 F2 复习）、「再来一轮」 |

**干扰项生成规则（重要）**

- 3 个选项**不能随机乱凑**，必须够像，否则是送分题
- **干扰项只能来自两处**：
  1. **相邻卦序**（该卦 ±1 至 ±3 卦之内）
  2. **同一上卦或同一下卦家族**（与该卦共享一个三画卦的卦）
- ⚠️ 说明：本期不做变卦与关联卦推演（见 4.2），因此**数据里不存在「关系卦」可用**，不要按互卦/错卦/综卦来取干扰项

**进度写入（本期唯一的「写入」功能）**

- 写入内容：**本轮成绩、累计答题数、累计正确数、错题列表（卦序号）**
- 存储位置：**云端数据库**（经匿名标识关联，见 F6 与 §7.3）；同时在本机留一份副本
- 必须支持「清空我的记录」按钮，且**本地与云端一并清除**
- 刷新页面、关闭浏览器再打开，记录必须还在
- **服务端不可用时的行为**：不得阻塞答题——进度先写本地，页面顶部提示「进度暂存本地，稍后自动重试」

**边界条件**

- 一轮固定 20 题，**同一轮内不出重复题**
- 64 卦全部可作为题面
- 答错后必须能立刻看到正确答案，不允许「等服务端返回」

**不做**

- 不做限时挑战（速度挑战）
- 不做闪卡记忆、不做配对玩法
- 不做排行榜、不做学习报告图表

### F5 · 来源标注组件（P0，复用于 F2）

**目的**：把「原文和解读分层可见」这条产品边界变成界面上的实物。

**形态**：每个文本块下方一行小字标注，包含三要素：

| 要素 | 示例 |
| --- | --- |

这是「不算命」在界面上的落地方式。参考 daooracle.life 的 `Source Tier + Registry ID + Reference` 设计，它证明了这种做法可行且必要。

### F6 · 学习进度存取（P0，v1.1 新增）

**目的**：让学习进度**不依赖某一个浏览器的缓存**，同时**不引入登录墙**。

**为什么不做登录**

research.md 的竞品结论已经指出：学习工具的第一大流失点是登录页。所以本期改用**匿名标识**——用户打开即用，系统在后台生成一个随机 ID 存在本机，用它关联云端进度。**用户全程看不到「注册」两个字。**

**页面元素**

| 元素 | 说明 |
| --- | --- |
| 进度显示 | 详情页 / 测验页显示：累计答题数、累计正确数、正确率、上次练习时间 |
| 同步状态 | 一行小字：`已同步` / `暂存本地，重试中` / `未同步` |
| 清空按钮 | 「清空我的记录」，**需二次确认**，并说明「本地与云端一并删除，不可恢复」 |

**数据流**

1. 首次访问 → 生成随机 `anonId` → 存本机
2. 用户答题 → **先写本机** → 再请求云端写入
3. 写云端失败 → 保留本机副本，标记待重试，**不弹错误框打断答题**
4. 打开页面 → 读云端与本机，**取更新时间较新的一份**用于展示

**边界条件**

- 云端与本机数据不一致时，以**更新时间较新**为准
- 匿名标识不含任何身份信息，且**不可反推用户身份**
- 同一浏览器清空缓存后 `anonId` 会丢失 → 进度无法找回，**必须在清空按钮旁明确告知**
- 服务端连续失败时，页面功能**完全不受影响**（答题、翻页、看卦全部照常）

**不做**

- 不做注册、登录、找回密码
- 不做跨设备同步（留 v2.0，依赖账号）
- 不做学习报告图表、不做排行榜
- 不做行为埋点与使用分析

### F7 · 起卦与解读（P0，v1.2 新增）

**目的**：给用户一个**主动打开这个产品的理由**，并把这份好奇**转换成去读卦辞爻辞的动作**。

**起卦方式：铜钱法（三枚）**

| 步 | 操作 |
| --- | --- |
| 1 | 页面出现三枚铜钱与一句提示：「静一静，掷六次」 |
| 2 | 每次点击「掷」，三枚各出正 / 反 |
| 3 | 按**背面朝上的枚数**定爻（**背 = 阳**，取通行约定）：3 背 = 老阳（变爻）、0 背 = 老阴（变爻）、2 背 = 少阳、1 背 = 少阴 |
| 4 | 从下往上依次成六爻，**第六次完成后自动进入结果页** |
| 5 | 全程**不收集任何输入**——页面上没有「你问什么」的输入框 |

**结果页结构（自上而下）**

| 顺序 | 元素 | 内容 |
| --- | --- | --- |
| 1 | 卦头 | 卦符（大图）+ 卦名 + 第几卦 + 上下卦 |
| 2 | **卦象图** | 六条爻线；**变爻用不同颜色加标记区分** |
| 3 | **第一层 · 卦象说什么** | 上卦下卦的自然意象 → 结构含义（如「上坤下艮，地在山上」） |
| 4 | **第二层 · 卦辞爻辞怎么讲** | 引原文 + 白话；**有变爻时突出显示该爻的爻辞** |
| 5 | **第三层 · 想跟你说的话** | 情绪引导，方向由卦的属性固定（吉戒骄 / 凶劝慰 / 平中性），**永远带「非原文」标注** |
| 6 | 边界声明 | 「本页不预测、不建议，请把它当作一段古文的解读」 |
| 7 | 去读全卦 | 一个按钮进入 F2 详情页——**把好奇导向学习** |

**关键约束**

- 三层解读**顺序不可调换**，第三层不得与第一二层混排
- 第三层文案**必须命中 §4.1.3 的方向表**，且不得出现「你会……」「建议你……」「宜 / 不宜」
- 变爻**只解释本爻的爻辞，不推演之卦**
- 起卦**不落库、不留历史**——不做「我的卦记录」。理由：起卦是即时体验，存下来反而暗示「你的卦很重要，要记住」，会把产品往迷信方向推

**边界条件**

- 起卦过程**必须能重掷**（用户可能手滑）
- 起卦**在本地完成，不依赖网络**；服务端不可用时照常可起卦

**不做**

- 不做蓍草法（流程太长）、不做数字起卦 / 时间起卦——**本期只留一种方式，避免选择困难**
- 不做变卦推演、不做互卦 / 错卦 / 综卦
- 不做「问题输入框」、不做解卦问答
- 不做起卦分享卡（属体验增强项）

## 7. 数据与内容来源要求

### 7.1 数据字段

`data/64卦.json`（由现有 `data/64卦总表.csv` 扩充），每条记录包含：

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| `id` | 必填 | 卦序 1–64 |
| `name` | 必填 | 卦名（如「谦」） |
| `symbol` | 必填 | 卦符（如 ䷎） |
| `pinyin` | 必填 | 拼音 |
| `upperTrigram` / `lowerTrigram` | 必填 | 上卦 / 下卦（卦名 + 自然意象） |
| `lines` | 必填 | 6 条爻，每条：阴阳 + 爻题 |
| `judgment` | 必填 | 卦辞原文 |
| `judgmentPlain` | 必填（值可为空字符串） | 卦辞白话；为空时界面显示「待补」，**不允许用原文冒充** |
| `image` | 必填 | 象辞原文 |
| `imagePlain` | 必填（值可为空字符串） | 象辞白话；规则同上 |
| `lineTexts` | 必填 | 6 条爻辞，每条含：爻题、原文、白话（可为空字符串）、小象 |
| `source` | 必填 | 原文出处（如 `ctext.org/book-of-changes`） |

> 「必填」的含义：字段**必须存在于 JSON 中**。标了「值可为空字符串」的字段允许为空，但界面必须显式显示「待补」，而不是留白或拿原文顶上。

### 7.2 内容红线

1. **原文必须来自公有领域版本**（王弼本，以 ctext.org 为准），每条标注出处
2. **白话必须有依据，宁可少译不可错译**；无把握的白话留空并标注「待补」
3. **不允许把后人解读混进原文区**
4. **本项目自己撰写的文字**（页面文案、白话解读、测验选项、按钮文字、F7 第三层）中，**禁止的是「预测性」与「建议性」表述，而不是「吉」「凶」这两个字本身**（v1.2 修正）
   - ❌ **禁止**：对未来的断言（「你会……」「今年有财运」）、对具体事项的判断（「适合换工作」「不宜出行」）、建议性表述（「建议你……」「宜……」「不宜……」）、运势类词汇（「运势」「旺」「衰」「犯太岁」）
   - ✅ **允许且必须有**：吉卦的戒骄文字、凶卦的劝慰文字（见 §4.1.3 方向表）；引用原文
   - 卦辞爻辞**原文本身就大量含「吉」「凶」「无咎」**（如谦卦爻辞「谦谦君子，用涉大川，吉」）——引用原文不受任何限制，但必须位于「《周易》原文」标注区内，原文区不得混入本项目的解读文字
   - **判定口径**：把 F7 第三层与所有白话解读逐句抽出来读，**每一句都必须能回答「这句话是在解释卦，还是在替用户判断世界？」**——凡是后者，即为违规

### 7.3 服务端数据与隐私（v1.1 新增）

**唯一要存进数据库的东西**是学习进度，字段如下：

| 字段 | 说明 | 是否必需 |
| --- | --- | --- |
| `anonId` | 随机生成的匿名标识（UUID），**与用户身份无关** | 必需 |
| `answeredTotal` | 累计答题数 | 必需 |
| `correctTotal` | 累计正确数 | 必需 |
| `wrongIds` | 错题卦序号列表（1–64） | 必需 |
| `rounds` | 每轮成绩（时间 + 得分），用于「看到分数变化」 | 必需 |
| `createdAt` / `updatedAt` | 创建与最后更新时间 | 必需 |

**绝不落库的内容**（硬性红线）：

- 姓名、手机号、邮箱、第三方账号、身份证件
- IP 地址、设备指纹、User-Agent 原始串、地理位置
- 任何行为埋点、点击流、停留时长
- **起卦记录**（起了哪一卦、什么时候起的）——见 F7「不做我的卦记录」

**用途限制**：数据**只用于**在页面上显示「你的学习进度」。**不做**用户画像、不做统计报表、不共享或出售给第三方、不用于任何模型训练。

**用户控制**：提供「清空我的记录」，本地与云端**同时删除**，不可恢复。

**合规提醒**：即使是匿名标识，只要能关联到具体个体的学习记录，仍属个人信息范畴。**上线前必须有隐私说明页**（写清：存了什么、不存什么、怎么删、找谁问），并在首次访问时以非打扰方式告知。

**成本约束**：本期**只用免费额度**——不开通按量计费、不设置预置并发。

**技术实现不在本文档内**，见 `docs/TECH_DESIGN.md`。

## 9. 风险与依赖

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| 1 | **卦象图的爻线容易画反**（从上往下 vs 从下往上） | 全部 64 卦错，产品直接不可用 | 先把 1 卦画对并用 64 卦逐条核对，作为阶段一的唯一硬指标 |
| 2 | **白话质量**：自己写容易出错，用现成的涉版权 | 内容可信度受损 | 优先找公有领域白话；无把握就留空并标「待补」，不硬写 |
| 3 | **数据录入量大**（64 卦 × 约 10 个字段） | 25 天里可能做不完 | 先保证卦名/卦符/上下卦/卦辞齐备；爻辞可分批补 |
| 4 | **中文搜索匹配范围失控** | 工期被拖长 | 本期搜索只做卦名 + 序号两种精确匹配 |
| 5 | 测验干扰项设计不当，题目变成送分题 | 记忆效果归零 | 干扰项优先取自相邻卦序或同卦家族 |
| 6 | 依赖 | — | 原文数据依赖 ctext.org 可访问；日常开发依赖本地环境可用 |
| 7 | **云资源产生预期外费用**（免费额度用尽 / 误开按量计费 / 误设预置并发） | 产生账单 | 只用免费额度；**不开按量计费、不设预置并发**；一切云资源相关操作**先停下与用户确认** |
| 8 | **服务端故障导致核心功能不可用** | 答题直接挂掉，用户流失 | F6 强制要求本地降级：云端不可用时答题照常，进度暂存本地并自动重试 |
| 9 | **匿名标识丢失**（清缓存 / 换浏览器）导致进度找不回 | 用户以为数据丢了 | 清空按钮旁明示风险；跨设备恢复留 v1.1 的「进度码」与 v2.0 的账号方案 |
| 10 | **被当成算命网站**（v1.2 新增） | 目标用户流失——**这是唯一真正的自毁路径** | 用结构而非口号区分：三层解读固定顺序 + 第三层必带「非原文」标注 + 结果页边界声明 + **起卦环节不提供任何「替用户做决定」的输入**（见 F7 关键约束）；验收见 8.2 F7 |
