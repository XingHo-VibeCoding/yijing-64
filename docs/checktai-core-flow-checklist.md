## 〇、名词映射（先读，避免对不上）

代码与 PRD 里**没有** `plan_days` / `checkins` / `打卡` 这些实体。PRD §7 明确「不做连续打卡排行」。
真实「检查台」在 **Records 页（`#/records`）** 内，是 Day 20 加的云端健康/探针面板，它只操作两类真实数据：

| 用户说的 | 真实对应 | 云端接口 |
| --- | --- | --- |
| 打开检查台 | Records 页底部「云端同步」区的检查台面板 | — |
| 读取 plan_days/checkins | 「重新读取」云端：读 `favorites`（收藏）+ `divination_records`（起卦记录）两个计数 | `GET /api/favorites`、`GET /api/divination_records`（带会话） |
| 写入打卡 | 「写入测试」：填 1–64 的卦序号 → 点「收藏这一卦」 | `POST /api/favorites` body `{hexagramId:N}` |
| 刷新确认 | 再点「重新读取」，看收藏计数是否 +1 | 同上 GET |
| 修改 | 检查台**无「原地改字段」入口**（PRD F8：记录不可改写）。等价做法 = 取消收藏 + 重新写入 | `DELETE /api/favorites/:hexagramId` + 再次 `POST` |
| 删除 | 两种：① 取消单条收藏（上文 DELETE）② 清空全部（二次确认「确定清空」） | ② `DELETE /api/me/data?scope=all` |

## 一、核心链路（正常路径，照顺序跑）

1. **打开检查台**
   - 步骤：浏览器地址栏进 `…/#/records` → 滚到底部「云端同步」区，看到「健康状态 / 写入测试 / 重新读取」。
   - 预期：面板正常渲染，无报错；初始计数显示当前云端条数。
   - 观察点：地址栏 URL 带 `#/records`；F12 Console 无红色报错。

2. **读取（确认基线）**
   - 步骤：点「重新读取」→ 等 1–2 秒。
   - 预期：出现「来自读接口 / 直连 rdb」状态；收藏计数 N、记录计数 M 显示出来。
   - 观察点：F12 Network 里应有 2 个 `GET /api/favorites`、`GET /api/divination_records`，状态 200。

3. **写入（打卡等价）**
   - 步骤：在「写入测试」输入 `5` → 点「收藏这一卦」。
   - 预期：下方显示 `卦 5 → HTTP 201 · 已新建 …`（首次）或 `HTTP 200 · 已收藏（幂等）`（已存在）。
   - 观察点：Network 里 `POST /api/favorites` 状态 201/200；响应体 `ok:true`。

4. **刷新确认**
   - 步骤：再点「重新读取」。
   - 预期：收藏计数 = 步骤 2 的 N + 1（若该卦原本未收藏）或不变（已存在，幂等）。
   - 观察点：计数变化与写入一致；不出现重复行。

5. **修改（等价操作）**
   - 步骤：到首页/总表对该卦「取消收藏」（走 `DELETE /api/favorites/5`）→ 回 Records 页「重新读取」。
   - 预期：收藏计数 −1；Network 里 `DELETE /api/favorites/5` 状态 204/200。
   - 备注：这是「改」的最接近真实操作；检查台本身没有另开修改入口。

6. **删除（清空）**
   - 步骤：点「清空我的记录」→ 弹二次确认 → 点「确定清空」→ 「重新读取」。
   - 预期：收藏计数与记录计数均归 0；Network 里 `DELETE /api/me/data?scope=all` 状态 200。
   - 观察点：清空后重读为 0，不残留；镀金（gilded）不参与清空、仍在。

### 找到并修复的真实 Bug：清空后立即写入的竞态（静默数据丢失）

- **现象**：点「清空我的记录」后立刻收藏一卦 → 界面显示「卦 N → HTTP 201 · 已新建」→ 几秒后收藏凭空消失；F12 Console **无任何报错**。
- **复现**：`clearAll()` 后立刻 `POST /api/favorites`（与检查台「收藏这一卦」同一路径），4.5s 后云端读取该行已不存在。重试第 1 次即复现：`HTTP 201 survived=false ids=[]`。
- **定位（排除法）**：
  1. 输入错？否——hexagramId 合法，接口返回 201（写入本身成功）。
  2. 网络错？否——同会话其余请求全 200。
  3. 服务端错？否——POST 201 是成功响应；DELETE 链路本身也验证过（204/200）。
  4. RLS 错？否——若 RLS 拒绝会返回 401/403 且界面可见，这里是 201 后消失。
  5. **前端时序**：`clearAll()` 的云端删除是 4 表串行 DELETE（在飞数百 ms~数秒），且走 `pushSilent`（fire-and-forget）；这期间新写入**不等它落地**直接发出 → POST 落在 favorites 表 DELETE 之前 → 被抹掉。← **真正原因**
- **修复**（仅 `src/storage.js`，一处问题）：
  - `clearAll()` 把在飞的清空 Promise 记为 `clearInFlight`（不再走 `pushSilent`，避免自等待死锁）；
  - `pushSilent()` 所有写入上推前 `await afterClearDone()`（覆盖收藏/记录/成绩/进度全部上推路径）；
  - `debugApiWrite()`（检查台写入测试）同样先等清空落地，与业务写入同权。
  - 方向只有这一侧：**写入等清空**；清空不等写入（用户最后动作是清空时，清干净才对）。
- **修复后**：同一流程 `HTTP 201 survived=true`；界面「收藏 1 条」稳定存活。全链路回归无回归。

### 测试脚本本身的教训（如实记录）

- 首轮 S1/B0/B7 失败**不是产品 Bug**：新端口首次加载要冷编译整个应用图（64 卦数据 + 全组件），14.2s 时页面未挂载完。修法：驱动等待 13s→20s + 页面内**轮询**等待 `.rec-check` 出现（替代固定 sleep）+ 空值保护防连锁崩溃。
- 纯 UI 流程（确定清空 → 收藏）中间有约 400ms 的 React 渲染延迟，POST 常落在删除之后而躲过窗口；模块级同序调用（~50ms 内打出）才稳定命中——**竞态窗口真实存在但极窄**，这也解释了为什么线上不易察觉。
