⚠️ **这一项补测里我连着犯了 6 次判据错误（如实全记）**，它们是本次最有价值的产出：

1. 判据 `/本卦判为|解读/` 会被**总表页**命中 → 假证明；
2. 改用 `/解读/` 仍被中间步骤「卦已成 · **解读之前**」命中 → 仍是假证明；
3. 改用「卦辞 + 象辞」，结果**总表页底部的数据来源说明里就写着「卦辞与象辞取自 GitHub sunls2/zhouyi…」** → 第三次假证明；
4. 最终判据 = 「第 N 卦 · 」+「本项目的理解 · 非原文」，总表页与中间步骤均不含 → 成立；
5. 点击用 `element.click()` 无效（题目相位由 `modeRef` 守卫），必须走 **CDP `Input.dispatchMouseEvent` 真实鼠标事件**，且要等云动动画结束（`modeRef` 回到 `idle`）才能点下一题；
6. 判「是否到达结果页」只写了有变爻时的文案「今天的卦已记录」，**漏了无变爻时的另一变体**「今天的第一卦已经记下了」→ 页面明明到了却被判成未到。

**结论（比判据更重要）**：这类自动化取证的失败模式，**六次全部是「判据写错」而非「产品坏了」**。**一个判据在被判为通过之前，必须先在不该通过的页面上试一次。**

## 三、结营复盘：28 天里最大的一个认知改变

**从「把功能做出来」变成「证明它是对的，而且知道自己还不知道什么」。**

28 天前我的默认动作是：写代码 → 跑起来 → 觉得没问题。28 天后我的默认动作是：写代码 → **先问「怎么证明它对」** → 跑 → 把判据本身也怀疑一遍。

这个改变是被真实打出来的，不是想出来的：

- Day 24 那个「清空后立即写入」的竞态，**界面显示成功、Console 零报错**——所有「看起来正常」的信号都是假的，只有写完回读才抓到。
- Day 25 做发布检查 Skill 时，Skill 入库后第一次当发布门就**自己命中自己**（检查器的源码也在扫描范围内）。
- Day 28 做验收，我的判据先失效：**POST 计数说 0、云端明明有数据**；**「是否进结果页」被总表页文本误命中**。
- Day 28 补测，我的判据又连错五次：总表页 → 中间步骤「解读之前」→ 总表页底部的「卦辞与象辞」说明文字 → 点错元素类型 → 卡住阈值早于点击冷却。**每一次都差点把假证明写成「已验证」。**

所以最大的收获不是「做出了一个易经应用」，而是这句：**证据必须独立于被测对象产生。** 页面显示的「已记录」不算，云端回读才算；代理日志里的请求数不算，数据库里的行才算；我自己写的判据不算，**在不该通过的页面上试过一次**才算。

**由此补上的一条可执行规则**：任何自动化判据，在写完的那一刻，先去它**不该命中**的页面上跑一遍。跑不通的判据，不是判据，是自我安慰。
