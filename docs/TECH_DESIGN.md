## 1. 方案总览

```
浏览器（React + Vite 构建的静态站点）
   │
   ├─ 读卦数据 ──→ 项目内 JSON（打包进前端，不走网络）
   │
   └─ 读写进度 ──→ CloudBase PostgreSQL
                     ├─ PostgREST 自动生成的 REST 接口（建表即得，无需写后端）
                     └─ 行级权限 RLS（每个匿名用户只能碰自己的行）
```

**关键结论：本方案大概率不需要写云函数。** CloudBase PG 的 PostgREST 会把表直接变成 REST 接口，配合 RLS 就能满足 F6 的全部需求。云函数只在出现「必须服务端计算」的逻辑时才补。

> 这是本期最重要的架构判断：**能不动云函数就不动**——少一层就少一个故障点和一份计费项。

## 2. 技术栈与选型理由

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 19 + Vite（**已实现**） | PRD 前已跑通；构建产物为纯静态文件 |
| 数据（卦） | 项目内 `data/64卦.json` | 数据量小且不变，打包进前端**零延迟、零请求、零计费** |
| 数据库 | CloudBase PostgreSQL | 用户指定。关系型、标准 SQL、建表即得 REST 接口 |
| 权限 | PostgreSQL RLS | 用同一套 SQL 表达「谁能看什么」，不需要自建鉴权服务 |
| 身份 | CloudBase 匿名登录（见 §5） | 满足「打开即用、无注册登录」，同时让 RLS 有主体可依 |
| 托管 | CloudBase 静态网站托管 | 用户指定。HTTPS + CDN，前端部署的最终归属 |

> **为什么卦数据不放进数据库**：64 条记录、约 15KB，放进数据库只会增加一次网络往返和一份计费项，还引入「数据库挂了就看不了卦」的风险。**放进前端打包产物是最优解。**

## 4. 数据库设计

### 4.1 表结构（示意，字段与 PRD §7.3 一一对应）

```sql
-- 学习进度主表：一个匿名用户一行
create table if not exists study_progress (
  uid            text primary key,               -- 匿名登录返回的用户标识
  answered_total integer not null default 0,
  correct_total  integer not null default 0,
  wrong_ids      smallint[] not null default '{}', -- 错题卦序号（1-64）
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);

-- 每轮成绩：用于「看到分数变化」
create table if not exists study_rounds (
  id         bigserial primary key,
  uid        text not null,
  score      smallint not null,
  total      smallint not null default 20,
  created_at timestamptz not null default now()
);

create index if not exists idx_rounds_uid_time on study_rounds (uid, created_at desc);
```

### 4.2 明确「不进数据库」的字段（照抄 PRD §7.3 红线）

姓名、手机号、邮箱、第三方账号、身份证件、**IP 地址**、**设备指纹**、**User-Agent 原始串**、地理位置、任何行为埋点 / 点击流 / 停留时长。

> **实现注意**：云函数或网关的默认日志**可能自动记录 IP 与 UA**。因此若最终需要写云函数，**必须确认日志级别与字段**，不能出现「业务表干净但日志里全是 IP」的情况。

### 4.3 行级权限（RLS）

思路：**每个用户只能看见和修改 `uid` 等于自己的那一行**。策略写法示意（**函数名待 V4 核实**）：

```sql
alter table study_progress enable row level security;

create policy "read own progress"   on study_progress for select using (uid = auth.uid()::text);
create policy "insert own progress" on study_progress for insert with check (uid = auth.uid()::text);
create policy "update own progress" on study_progress for update using (uid = auth.uid()::text)
                                                                 with check (uid = auth.uid()::text);

alter table study_rounds enable row level security;
create policy "read own rounds"   on study_rounds for select using (uid = auth.uid()::text);
create policy "insert own rounds" on study_rounds for insert with check (uid = auth.uid()::text);
```

> 若 V4 确认函数名不同，只需替换 `auth.uid()`，策略结构不变。

## 5. 身份方案：用平台自带的匿名登录，而不是自己造 ID

**PRD 的原始设计**是我在 PRD 里写的「自造 `anonId` 存本地」。**核实平台能力后，我改用更好的做法。**

| | 方案 A · 平台匿名登录（**推荐**） | 方案 B · 自造 anonId（PRD 原始描述） |
| --- | --- | --- |
| 怎么做 | 调用 CloudBase 匿名登录，拿到标准用户标识 | 前端 `crypto.randomUUID()` 生成，存 localStorage |
| RLS 能否生效 | ✅ 能，权限由数据库层强制 | ❌ 不能，标识由前端自报，**可被伪造** |
| 需要写后端吗 | 不需要 | 需要云函数校验，且校验逻辑本身要靠传参信任前端 |
| 用户感知 | 无感知（不是登录页） | 无感知 |
| 换设备 / 清缓存 | 一样会丢 | 一样会丢 |

**结论：选方案 A。** 它同样满足 PRD「打开即用、无注册登录、不采集身份信息」，但多了一层**数据库层强制的数据隔离**——方案 B 的安全性完全依赖前端自觉，这在生产上不可接受。

> **PRD 需要同步**：PRD §6 F6 与 §7.3 写的是「随机生成的匿名标识」。功能语义完全一致，但实现主体从「前端自造」变为「平台匿名登录」。**这是一处实现细节的修正，不改产品行为**；我会在 PRD 变更记录里补一行说明。

## 6. 接口设计

### 6.1 读进度

```
GET /study_progress?uid=eq.<当前用户>&select=*
```

### 6.2 写进度（答题后）

```
POST /study_progress          # 首次：插入
PATCH /study_progress?uid=eq.<当前用户>   # 后续：更新
```

### 6.3 每轮成绩

```
POST /study_rounds
GET  /study_rounds?uid=eq.<当前用户>&order=created_at.desc&limit=10
```

> 以上是 PostgREST 的通用查询语法（`eq` / `order` / `limit`）。**实际路径前缀与鉴权头需要以 CloudBase PG 的接口文档为准**——这是 §3.2 V4 的延伸待核实项。

### 6.4 什么时候才需要云函数

只有两种情况：
1. **需要跨行事务的统计**（如全站正确率分布）——本期不做，PRD §6 F6 已明确「不做学习报告图表」
2. **需要隐藏的密钥调用**（如接第三方服务）——本期没有

**因此本期计划：不写云函数。**

## 7. 前端集成与降级策略

### 7.1 数据流（对应 PRD F6「数据流」4 步）

1. 首次访问 → 匿名登录 → 拿到用户标识
2. 用户答题 → **先写 localStorage** → 再请求云端写入
3. 写云端失败 → 保留本地副本 + 标记待重试，**不弹错误框**
4. 打开页面 → 读云端与本地，**取更新时间较新的一份**

### 7.2 降级是本方案的强制要求

PRD 把「服务端不可用时答题照常」写成了验收项，所以：

| 场景 | 期望行为 |
| --- | --- |
| 无网络 / 数据库不可达 | 答题、看卦、翻页**全部照常**；顶部显示「进度暂存本地，重试中」 |
| 匿名登录失败 | 退化为**纯本地模式**，功能不减，只失去云端同步 |
| 网络恢复 | 自动把本地暂存的进度补写上去 |

**实现要点**：所有云端调用都必须包在超时 + 静默失败里，**任何云端异常都不能阻断用户的答题动作**。

### 7.3 前端依赖与构建

- 新增依赖（用于 PostgREST 调用）：以 CloudBase 官方 SDK 为准，**待 V4 核实后确定具体包名**，不预先写死
- `vite.config.js` 无需代理（云端为独立 HTTPS 域名）
- 构建产物：`dist/`

## 8. 部署方案

### 8.1 前端（静态网站托管）

```
npm run build                 # 产出 dist/
tcb hosting deploy dist -e <环境ID>
```

> `tcb app deploy --framework vite -e <环境ID>` 可一条命令跑完「装依赖 → 构建 → 上传」，适合本地不方便构建时使用。

### 8.2 访问地址

环境 ID 形如 `xxx`，默认域名为 `<环境ID>.xxx.tcloudbaseapp.com`（**具体域名规则以控制台实际显示为准**）。

### 8.3 密钥与配置安全

- **不把任何密钥写入仓库**：`.env` 已在 `.gitignore` 中，且本方案**前端不需要密钥**（匿名登录 + RLS 的设计目的就是为了不需要在前端放密钥）
- 若后续确实需要服务端密钥，一律放**云函数环境变量**，不进前端、不进仓库

## 9. 成本控制（对应硬约束 1）

### 9.1 免费档事实

| 项 | 数值 |
| --- | --- |
| 价格 | ¥0 / 月 |
| 资源点 | 3,000 点 / 月（1,000 点 ≈ ¥1） |
| 环境数 | 每账号 1 个免费环境 |
| **按量计费** | **官方明确：免费档不可用资源包与按量计费** ← 天然满足约束 1 |
| 续期 | 免费档需续期，**有到期时间**（具体以控制台为准） |

### 9.2 ★ 最大成本风险：PG 的 CPU 计费

计费项：`PostgreSQL CPU 使用量 342 点 / 核·小时`。

**极端情形**：若一个 1 核实例持续运行一个月——

```
720 小时 × 342 点 = 246,240 点     而免费额度只有 3,000 点/月
```

**这不是 24 倍的问题，是 82 倍。** 但官方博客称空闲时会挂起计算资源，且「共享实例按使用计量」。**所以真实消耗取决于 V3 的两个未知数：空闲多久会挂起、共享实例的实际计费口径。**

### 9.3 因此设定的操作红线

1. **绝不开通按量计费**（免费档本来也不支持，但升级按钮不要点）
2. **绝不设置预置并发**（会导致常驻计费）
3. **建库后第一件事是看控制台的资源点消耗**，观察 24 小时的真实走势再继续开发
4. **若发现 PG 的 CPU 计费按常驻计算**：立刻改用「前端全本地存储」的降级形态，**F6 的云端部分暂缓**，并在 PRD 里记一笔——**产品功能不受影响，只是回到 PRD v1.0 的存储方式**
5. **免费环境有到期时间**，到期前需续期，否则环境进入停服隔离期

> 这一节是我建议**在动手前先单独确认**的部分。原因很直接：**功能可以实现的东西，不等于成本上划算的东西。**
